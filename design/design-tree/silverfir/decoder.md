- Function code is decoded by streaming, not by building an instruction list:
  a single pass walks the code bytes, and for each instruction reads its
  opcode and immediates and calls back through a handler trait
  (`OpcodeHandler`). No materialized instruction vector exists between decode
  and consumer.

- The decode walk fans out to several handlers at once: a decoder object holds
  a list of registered handlers (`Decoder`) and notifies every one of them per
  opcode, so independent observers (validator, disassembly printer) sit side by
  side on a single walk rather than one consumer embedding and forwarding to
  the others.

- The handler trait has decode-lifecycle hooks (`on_decode_begin`,
  `on_decode_end`) bracketing the per-opcode callbacks, so a handler can set up
  per-function state and run a finalization pass over what it accumulated.

- Each per-opcode callback receives both the opcode's own byte offset and the
  byte offset of the following opcode, so a handler can resolve forward jump
  targets to the instruction after a control construct.

- The opcode universe is split by prefix into three spaces — the single-byte
  base opcodes, the `0xFC` (saturating/bulk) extension, and the `0xFD` (SIMD)
  extension — and a wrapper enum tags which space an opcode came from so one
  handler entry point dispatches all three.

- The base and extension opcode tables are generated by a macro from a single
  declaration list, which emits an enum variant (carrying the byte value) and a
  display name per opcode from one source of truth; the decoder and its
  consumers match on the enum, not on raw bytes.

- Each instruction's immediate operands are decoded into a tagged immediate
  value handed to the consumer alongside the opcode (`Immediate`); the decoder
  owns the per-opcode knowledge of how many immediates of which kind to read.
  The immediate's tag names the Wasm-level role of the operand (label index,
  function index, memarg, call-indirect args, …), not its raw byte shape, so a
  consumer reads meaning without re-deriving it from the opcode.

- A block type immediate is decoded out of the spec's compressed s33 form: the
  empty type, a single inline value type, or a positive type index, normalized
  into a three-way tag (`BlockType`) before it reaches the consumer.

## Moves

- 2024-02-01 (5bb02079) replaced [[single-handler-decode-fn]]: a
  single-consumer decode function cannot express several independent observers
  of one decode walk — it forces one consumer to embed and hand-forward to the
  others; a decoder object holding a vector of handlers fans every opcode out
  to all registered observers, so validator and printer become sibling handlers
  on one walk (diff).

- 2024-01-30 (80306a9a) dropped: per-opcode named byte constant — the macro
  stopped emitting the `pub const NAME: u8 = value` form once decode and its
  consumers matched on the generated enum variant instead of raw bytes; the
  enum variant carries the byte value, so the parallel constant was redundant
  (diff).
