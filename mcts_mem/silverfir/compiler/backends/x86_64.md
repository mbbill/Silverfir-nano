- The x86_64 backend's FP dynamic bank starts at XMM2; XMM0 and XMM1 are
  reserved as the 2-lane FP scratch pool; the allocator never hands out a lane
  the inline FP sequences (Neg / Min / Copysign) scribble into as a
  mask/negation temp, with a compile-time assertion that `fp_dynamic + fp_scratch
  == 16`, disjoint (`new_fp_scratch_pool`).

## Facts

- 2026-04-19 (c7818939) pitfall: x86 packed-integer/float SIMD binary ops are
  destructive 2-operand (dst is also an input), so when dst aliases the rhs
  register the lowerer must copy rhs into an FP scratch before the op; this
  preserve step is needed only for the native-vector lowerings, not for paths
  that round-trip through the stack or use literal XMM temporaries (code).

- 2026-03-16 (40701e7c) pitfall: x86_64 SSE float arithmetic is destructive
  two-operand (dst = dst OP src), so the lowering moves lhs into the result
  register first; when the result register aliases rhs (result == rhs and result
  != lhs) that initial move clobbers rhs, so rhs must be snapshotted into an FP
  scratch before lhs is materialized into the result — the same rhs-before-lhs
  hazard the 32-bit pair bitops have, here from the SSE two-operand form (code).

- 2026-03-16 (f9695683) pitfall: a backend-emitted C helper call
  (trapping/saturating truncation) clobbers all caller-saved GP transient
  registers, and unlike a wasm-level call boundary nothing else spills them, so
  the x86_64 backend must push/pop its 7 GP transients (plus one padding push for
  16-byte System V stack alignment) around the helper and save the result
  register before restoring; arm64 needs no such save because its truncation
  helpers leave the live transients alone (code).

- 2026-03-16 (f9695683) pitfall: x86 variable shifts force the count into CL
  (RCX), so getting lhs into dst and rhs into RCX is a two-element parallel move
  that can cycle (lhs already in RCX while rhs is in dst); the lowering resolves
  both source registers first, then orders the two moves by conflict (rhs->RCX
  first when rhs==dst, swap via scratch when both conflict) rather than moving
  lhs->dst unconditionally, which previously clobbered rhs when rhs lived in dst
  (code).

- 2026-03-18 (db7df58f) pitfall: x86_64 float compare and float-compare-branch
  emission must pick the rhs FP scratch register relative to where lhs landed:
  always staging rhs in FP_SCRATCH1 clobbered a live FP transient when lhs had
  already been mapped into a real FP register, corrupting results; the fix
  chooses FP_SCRATCH0 for rhs when lhs is not already in FP_SCRATCH0 (else
  FP_SCRATCH2), which is what made x86_64 pass the spectest (code).

- 2026-03-25 (2d0838c7) pitfall: the System V trapping-truncation helper returns
  a 2-field {status,value} u64 struct in RAX:RDX, but the Microsoft x64 ABI
  returns a 16-byte struct via a hidden caller pointer rather than in RAX:RDX, so
  Windows needs a separate helper variant that takes an out-pointer (RSP-relative
  scratch slot passed in the 4th arg register R9) and returns only a u32 status
  in RAX (code).

- 2026-04-08 (a1906ede) pitfall: Wasm branch and trap-if conditions are i32
  values, but on x86_64 a GpWord carrier register can hold a stale upper 32 bits
  from a prior i64 value; testing the condition with test_rr_64 (the full 64-bit
  register) would let that stale high half make a logically-false condition test
  non-zero, taking the wrong branch — the fix tests with test_rr_32 so only the
  low 32 bits decide, and reading a cache register as a branch/trap condition is
  rejected as an internal error rather than silently mapped (code).

- 2026-04-14 (e4be6c9b) pitfall: emit_trapping_trunc_call wrote the ctx pointer
  into C_ARG0 (RCX) before moving src into C_ARG1 (RDX); because the x86_64
  backend-owned GP scratch bank is {RAX, RCX, RDX}, src regularly lives in RCX,
  so writing ctx into RCX first destroyed the float bits before the C_ARG1<-src
  move could forward them — the fix reads src into C_ARG1 first, and the durable
  rule is that at a C-ABI helper boundary an argument whose source register
  aliases a later destination must be staged before that destination is
  overwritten (code).

- 2026-04-19 (c7818939) rationale: signed lane equality/ordering compares
  (EQ/NE/LT_S/GT_S/LE_S/GE_S) lower to native packed compares
  (pcmpeq*/pcmpgt*), while the unsigned SIMD compares have no direct packed
  instruction and keep a scalar-emulated lowering (code).

- 2026-06-20 correction: the f9695683 Fact's "7 GP transients plus one padding
  push" is stale. Since RAX/RCX/RDX became backend-owned (a1906ede), the x86_64
  backend saves/restores 6 caller-clobbered GP dynamic transients
  (RSI/RDI/R8/R9/R10/R11) around the truncation helper with no padding push —
  6*8 = 48 bytes is already 16-byte aligned (code).
